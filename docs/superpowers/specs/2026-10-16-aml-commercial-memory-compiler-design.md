- **日期**: 2026-10-16
- **状态**: 待用户评审

## 3. 总体架构

```
Add（每 chunk ~20 条消息，request_id 幂等）
 ├─ L0 原文层（现状保留）: message 级原文 + Speaker/Date 前缀 + BM25 + bge-small 向量
 ├─ L1 记录层（新建，flash 档 LLM）: 单轮多类型提取 → 接地校验 → 六类类型化记录
 └─ L2 派生层（新建，纯代码）: 取代链/墓碑 · 时间线 · 实体图 · 集合视图（Add 时增量构建）

Search（每题）
 ① 查询分析（LLM）→ 多维路由标签 + 检索计划
 ② 多路召回：骨干=现有混合检索（全保留）；按路由加开 结构化路径（集合/时间线/取代链）
 ③ 组装（LLM）：权限收窄（选择/排序/合并/排版，禁创作）+ 算术外置 Python
 ④ 质量门：接地复核 · 卡型互斥 · 分区预算 · 逐字保真后检
 ⑤ 输出：Z0 视图卡区 / Z1 直接证据区 / Z2 支撑区
```

### 3.1 实施宿主
新系统在 `mermory_code/` 开发（`aml-system/` 的完整克隆，延续 git 历史；老仓库保持开源榜提交态不动，远程 `baseline` 指向它以备 cherry-pick）。FastAPI 端点与部署形态不变，L1/L2 以新模块挂在 `app/` 下，所有新路径用环境变量开关（沿用现有 DENSE/INJECT/PERSONA 开关模式），保证任一组件可独立回退为零 LLM 行为。开发期新配置独立于提交版 Dockerfile 固化值。

## 4. Add 端设计：记忆编译

### 4.1 L1 提取：单轮多类型
- **一次调用提取全部六类**（同一句"我上周搬去巴黎了"同时是 fact/event/supersede，拆轮会重复且互相矛盾）
- temperature=0，JSON schema 约束输出；每 chunk 一次调用
- 每条记录强制携带 `quote`（逐字原文片段）+ `source_mem_ids` + `session_id` + `timestamp`
- 全部结构挂在 user_id 命名空间内（库内绑定）

### 4.2 六类记录 schema（字段级）

| 类型 | 字段 | 用途 |
|---|---|---|
| `fact` | entity, attribute, value, time, polarity(肯定/否定/将来), quote, src | A 维无损抽取；实体图/取代链的砖 |
| `event` | who, action, what, when, where, outcome, seq_in_session, quote, src | 时间线砖块（C/F1） |
| `preference` | holder, domain, preference, strength, background_fact(健康/家庭/职业/关怀), quote, src | E 维 |
| `rule` | **verbatim_text(逐字)**, trigger_conditions, scope, ordered_steps[], quote, src | G2/G3（规则必须逐字保真） |
| `supersede` | entity, attribute, old_value, new_value, change_time, old_src, new_src | D1（取代链，替代正则三重门控） |
| `tombstone` | entity, attribute/scope, declared_time, quote, src | D3（删除/遗忘声明 → 标记不物理删） |

### 4.3 L2 派生层（纯代码聚合，非 LLM）
- **取代链**：新 fact 到达 → 查 `(entity, attribute)` 倒排 → 值冲突则挂链；链尾=当前值
- **时间线**：每库全序事件表（timestamp, session, seq）
- **实体图**：fact 的 (entity, relation, entity) 三元组挂边
- **集合视图**：`(entity, 集合类)` 成员累积表 + 首次出现时间（**Add 时增量构建**，决策点 2）

### 4.4 四道准确闸（anti-poison，生死线）
1. **逐字引用核对**：quote 必须在源文本中字符串级命中，否则整条丢弃
2. **只准显式陈述**：prompt 限定只记录引文直接支持的内容，禁止推断（隐含信息留给 L0 + answer 模板第 2 条的 episodic 推理）
3. **高风险二次复核**：将进入 LATEST/取代链的记录，用一次便宜调用对新旧值双向核对
4. **失败降级**：schema 失败/超时 → 该 chunk 只存 L0，行为退化为现有系统。**提取层永不阻塞、不污染入库**

### 4.5 模型档位（决策点 1）
- Add 端：**flash 档**（DeepSeek / Gemini Flash / GPT-mini 级）——抽取是模式化任务，质量足够，成本差 10 倍
- 接地校验：同档
- premium 档只留给 Search 端组装与最终提交跑

## 5. Search 端设计：证据包编排

### 5.1 查询分析（1 次 LLM，~1k tokens）
**四轴多标签**（粗标签保准确率，可叠加）：

| 轴 | 取值 |
|---|---|
| answer_shape 答案形态 | single-value / list / count / yes-no / interval-date / opinion / likely-abstain |
| depth 推理深度 | single-hop / chain / aggregation |
| temporal 时间模式 | none / point / order / interval-arith / latest-state |
| sensitive 敏感标记 | none / health-finance-identity |

- **规则先行，LLM 兜底**：when/how long/before/after→时间线索；list all/how many→枚举线索；options 存在→选择题；实体用现有 entity_index。规则给底线，LLM 处理长尾
- **离线校准**：用本地带标问题（LoCoMo cat1-4 / LME question_type / CLBench 任务类型）把分析器校准到接近 100% 再上线
- 分析器输出含**检索计划**（实体、属性、时间范围、选项），不只是标签

### 5.2 路由表（7+1 主路由，Z0 卡互斥）
| 路由 | 触发 | Z0 卡 | 打包策略 |
|---|---|---|---|
| R0 兜底 | 低置信 | 无 | 宽召回 + 纯重排（≈现有系统+重排） |
| R1 精准点查 | 单值单跳 | 无/极少 | 5–20 条精筛 |
| R2 枚举聚合 | 列表/计数/摘要 | SET VIEW 预聚合卡 | 完整集合+去重+排序 |
| R3 状态解析 | "现在/最新" | LATEST 卡（链解析） | 当前值+变更史 |
| R4 时序 | 排序/区间 | 时间线卡+区间预算卡 | 时段事件段 |
| R5 链式 | 多跳/因果/流程 | 链路衔接卡 | 分解→逐跳→推理序装配 |
| R6 偏好画像 | 偏好/背景 | 画像档案卡 | 偏好+背景记录 |
| R7 弃权/敏感 | 疑似无答案/敏感域 | 无 | 最小充分/极简返回 |

**误判必须便宜**：Z1 直接证据区永远来自对原始 query 的混合召回（与路由无关）；路由只影响 Z0 卡与打包策略。误判最坏结果 ≈ 现有系统行为，不会崩。

### 5.3 多路召回
- **骨干（全部保留）**：BM25 + bge-small RRF（`1.0/(60+dense) + 0.5/(60+bm25)`）+ 种子 top-20 + 邻居 ±1 + 实体两阶段扩展
- **新增结构化路径（按路由启用）**：实体集合路（键查找）/ 时间线路（范围查询）/ 取代链路（键→链行走）——均为精确查找，非相似度
- **召回量与返回 k 解耦**：内部宽召回，输出按路由窄打包
- **结构不整块进包**：实体图永不整体出现，只有被问实体的集合/链条切片进包

### 5.4 组装（1–2 次 LLM，读候选 5–15k tokens）
- **权限四件事**：选择、排序、合并、排版。**禁创作**——包里每行必须溯源到 L0 消息或 L1 记录；融合条目只能是源引文的拼接/缩写，数字/专名/日期逐字保留
- **算术外置**：计数、区间运算、去重在 Python 对结构化记录做（教训：计数 probe LLM 选条目 0% 吻合、中位偏差 30 倍——LLM 永不碰数数），LLM 只排版算好的结果
- **不对称风险**：弃卡→退化为现有行为（无害）；错卡→毒害判卷（行业榜低于随机线实证）。存疑即弃卡

### 5.5 质量门（四件套，新建；升级现有规则闸）
| 门 | 内容 |
|---|---|
| 接地复核 | Z0 卡出场前"声称 vs 引文"核对（与入库侧同机制） |
| 卡型互斥表 | 冲突卡型按路由独占（LATEST vs 时间线 vs 冲突卡对同一实体显式 mutex） |
| 分区预算 | Z0 ≤15% / Z1 ~60% / Z2 ~25%，硬上限 |
| 逐字保真后检 | 派生卡内所有数字/专名/日期必须在被引源文逐字出现，否则弃卡 |
| 路由决策日志 | 每次组装留档（路由/卡/理由），本地按路由出分归因 |

### 5.6 防震荡架构（震荡三定律的解药）
```
┌ Z0 视图卡区（≤15%）── 只放当前路由对应的结构化卡，卡型互斥
├ Z1 直接证据区（~60%）── 混合召回骨干 + 重排剪枝（路由无关的保底）
└ Z2 支撑区（~25%）────── 上下文/邻居，剪得最狠
```
一题一路由（+可选副路由），由逐题 LLM 决策，不是全局开关 → 不同题型在结构上不可能互相干扰；D4 的选择性与 F1 的穷尽性不同场，不再互为代价。

## 8. 合规红线（设计内嵌，非事后检查）
1. 派生卡一律**数据形态 + mem-id 溯源**，沿用已过评审的 LATEST 卡模式
2. Add 端视图与问题无关（是记忆不是答案）；Search 端预计算以"带出处的派生证据"呈现，不写成最终答案句式
3. 数字/专名/日期逐字保真（也是质量要求）
4. 不跨 user_id、不硬编码、不注入行为指令（强指令下本就无效）
5. 评测数据不训练/不分析/不重建（官方 rules）
